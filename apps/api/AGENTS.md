# apps/api — Veracand Node.js Backend

- Framework: NestJS 11. The api is the only writer of domain tables.
- Layering: `controller -> service -> repository -> db`. No DB calls in controllers.
- Errors: a repository raises a domain error that extends `NotFoundError` or `ConflictError` (`src/common/domain-errors.ts`) and knows nothing about HTTP; `AllExceptionsFilter` maps the kind to 404 or 409 with the error's message. Services let these pass: no catch-and-rethrow. A service throws a Nest `HttpException` itself only for what it decides (a 400 on the request's content, a 422 for a ledger refusal).
- A portfolio's ledger is written in one place, `OrdersRepository.transact`, which settles the portfolio first. Don't add a second write path.
- An order is checked twice: at placement by `trading/risk.ts` (an estimate; a refusal is a 422 and nothing is stored) and at its fill by the ledger. `preview` in `trading/settlement.ts` is the one function behind both the 422 and `POST .../orders/preview`; don't give the preview endpoint its own logic.
- An order asked for in dollars (`amount` instead of `quantity`) is turned into shares inside `preview` (`sharesFor` in `trading/risk.ts`), at the price the estimate uses and under the same lock. Everything after that works in shares; `orders.amount` only records what was asked. Don't size an amount anywhere else.
- The session clock (`trading/market-hours.ts`) is pure: the exchange calendar is loaded by `MarketCalendarService` and passed in. A date the calendar doesn't cover falls back to weekdays, 09:30 to 16:00. `GET /api/market/status` is that clock too (`marketStatus`); don't answer it from anything else.
- DB access: Prisma only. Use Prisma Client for models, Prisma Migrate for every schema change, and TypedSQL (`$queryRaw` as fallback) for hand-written candle and analytics queries. Hypertables and other TimescaleDB DDL go in `migrate dev --create-only` migrations edited by hand. MongoDB (Phase 4+) uses a second Prisma client with the MongoDB connector, not Mongoose. Don't add another ORM, query builder, or migration tool.
- The Prisma Client in `src/generated/prisma` is generated on install (`postinstall`) and gitignored: never commit it. Migration folders keep the name Prisma gives them (`YYYYMMDDHHMMSS_name`, 14 digits), since Prisma applies them in name order; rename one only before it reaches a shared database.
- Market data comes through `MarketDataProvider` (`src/market-data/provider/`, ADR 0010) and is written only by `IngestionService`. An adapter returns raw bars and unadjusted dividends in the database's conventions and throws only `ProviderError`; don't call a provider client from a service, and don't add a fallback from one provider to another. A new or changed adapter must pass `provider.contract.spec.ts` against a fixture made by `fixtures:record`. The asset list and the exchange calendar are Alpaca's and stay outside the contract.
- Market data is wired once, in `MarketDataCoreModule` (`src/market-data/market-data-core.module.ts`): the api server's `MarketDataModule` adds the controller on top, the CLIs and the worker use it directly or through `JobsModule`. Add a market data provider there, not in each.
- A command-line entry point is `runCli(...)` from `src/common/cli.ts` (it builds the module, closes it, and sets the exit code); the worker is the one exception, since it stays up. A symbol's whole history is `fullHistory()` (`src/market-data/history.ts`), and an unknown error becomes text through `errorMessage` (`src/common/error-message.ts`).
- Jobs/queues: BullMQ on Redis, used directly (`src/market-data/jobs/`). A job's payload is a Zod schema in `market-data.jobs.ts`; its work goes in `MarketDataProcessor`, which knows nothing of Redis, and must be safe to run twice. Throw `UnrecoverableError` (or a non-retryable `ProviderError`) for a failure a retry can't fix: the worker dead-letters it at once. The worker is its own process (`pnpm --filter @astraq/api worker`), not part of `AppModule`.
- Scheduling: no cron expressions and no in-process timers. Work that follows the market is a delayed job timed from the exchange calendar (`jobs/session-scheduler.ts`): one `session-close` job per session, added by id (`MarketDataQueue.addOnce`) so asking twice is harmless. To run something after other jobs finish, make it the last job of a flow (`MarketDataQueue.addThen`), not a job with a guessed delay.
- Data quality: a new check is a method on `DataQualityRepository` that returns a count and a capped sample, a count column on `data_quality_runs`, and a name in `DataQualityCheckNameSchema`. Checks report; they don't repair or block.
- Derived market data: `candles_daily` is compressed after 90 days and `candles_weekly` is a continuous aggregate of it (migration `20261125120000_candles_compression_weekly`). Bars are written only through `IngestionService`, which refreshes the weeks it wrote; a write that goes around it leaves the weekly bars stale until the hourly policy. The aggregate holds raw prices: read it through `CandlesRepository.findWeekly`, which handles the weeks an ex-date falls inside, never by multiplying its rows by a factor yourself. No retention policy on daily bars.
- Cache: `MarketDataCache` (`src/market-data/cache/`) over `CacheStore` (`src/common/cache-store.ts`), for display reads only. Never price an order, a valuation, or a settlement from it. A new cached read needs a TTL, a version in its key, and an invalidation in the writer of the data it caches; the store must stay fail-open (a Redis error is a miss). This Redis is the queue's and runs `noeviction`: no key without a TTL. A spec whose module reaches the cache overrides `CacheStore` with `NoCacheStore`.
- Raw payload archive: MongoDB through the official `mongodb` driver, not Prisma (`src/market-data/archive/`, ADR 0011). A provider call that should be archived runs inside `RawArchive.capture(...)`, and an adapter's `fetch` and clock come from `provider/capture.ts`; never write to the archive from an adapter. It is optional and fail-open: no `MONGODB_URL` means `NoRawArchive`, and a failed write is a warning, never a failed job. Insert and read only; expiry is the TTL index. Nothing may serve a request or price anything from it.
- Admin endpoints live under `src/admin/` behind `JwtAuthGuard` then `AdminGuard` (`ADMIN_EMAILS`; roles come in Phase 7). The api server reads the queue through `QueueAdminService`, which makes its `MarketDataQueue` on first use so the server still boots without Redis; it never enqueues or works jobs.
- Validation: Zod schemas shared from `packages/shared`; use `nestjs-zod` for DTO binding.
- Logging: pino with request-id middleware. No `console.log` in production paths.
- Tracing: `src/tracing.ts` sets up OpenTelemetry and must stay the first import of `main.ts` (instrumentations patch modules as they load). Make a span of your own with `inSpan` from `common/span.ts`, which needs only `@opentelemetry/api` and is a no-op in tests and the CLIs. Don't import `tracing.ts` anywhere else.
- OpenAPI: `@nestjs/swagger` + `nestjs-zod`. Every handler declares `@ZodResponse({ status, type })`; controllers add `@ApiProblemResponses()`. `pnpm contract` (root) writes `openapi.json` and regenerates `packages/sdk`; commit both. CI fails on drift. See ADR 0004.
- Python jobs (backtests, forecasts): enqueue via BullMQ; persist the returned result in the api.
